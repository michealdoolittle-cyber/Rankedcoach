# Full Codebase Cleanup — Dead Code, Performance, File Organization

**Status (2026-07-11 implementation):** Root debug artifacts were removed and ignored, the repeated `.nav-right`, `.nav-left`, and `.nav-btn` exact-rule blocks were consolidated with a visual-audit pass after each selector, and all 46 dead-function candidates were removed only after confirming each declaration had no other reference across public JavaScript or inline HTML. Theme Builder extraction is parked rather than forced: a deeper scan found roughly 440 `themeBuilder` references plus launch-locked code that still closes over live app-local auth, profile, layout, and override helpers. A safe extraction needs an explicit dependency interface first; moving the block directly into a standalone script would create dangling lexical dependencies despite the UI gate.

## 1. Duplicate CSS blocks — highest value, proven bug source, do this first

**Confirmed via direct count, not the old "6-9" estimate from earlier sessions — it's grown:**
- `.nav-right{...}` — **18 separate, non-adjacent rule blocks** in `app.css` (line numbers: 4232, 5850, 6890, 18542, 18547, 23641, 29349, 29531, 34985, 35024, 36024, 36601, 38132, 39362, 49668, plus others).
- `.nav-left{...}` — 7 separate blocks.
- `.nav-btn{...}` — 9 separate blocks.

This is not a new finding — `testing/visual-audit/CORRECTIONS.md`'s maintainability note flagged this pattern back on 07-06 as the likely root cause of the Ask Coach mobile bug, and it was later **confirmed** as the actual root cause of the crosshair-animation-always-plays bug (`notes/mobile-bug-fixes-2026-07-08.md` #4). Every one of these selectors resolved only by CSS source-order last-wins, not intentional cascade — every future change to any of these selectors is a gamble on which block actually wins, and this has already caused at least two shipped bugs this project has had to hunt down individually.

**Directive:** Consolidate each selector into exactly one rule block (or a clearly-commented, intentional small set if there's a genuine reason for more than one — e.g. a `body.is-mobile-layout` variant is legitimate, ten near-duplicates of the same mobile variant are not). Do this selector-by-selector, testing after each one (re-run `testing/visual-audit/audit.js` after every consolidation, not just once at the end) — this is exactly the kind of change that silently breaks something if done carelessly, given how many things apparently depend on the specific source-order winner today. Budget real time for this; it's tedious, not conceptually hard.

## 4. File organization — the Theme Builder extraction is the one safe, high-value structural move

`notes/structure.md` (written 2026-07-05, never acted on) already flagged `app.js` as too broad, mixing UI/data/copy/persistence/layout in one file, and recommended splitting concerns gradually rather than a risky full rewrite. Confirmed tonight: **the Theme Builder feature alone accounts for 162 references to `THEME_BUILDER_*` spanning a huge portion of the file — and it's provably inactive for every user right now** (`THEME_BUILDER_LAUNCH_LOCKED = true`, confirmed earlier this session). This is the safest possible large-scale extraction: moving genuinely dead-weight-for-now code out of the critical-path file has essentially zero functional risk, since nothing currently reachable depends on it being inline.

**Directive:** Extract the Theme Builder feature into its own file (e.g. `public/theme-builder/index.js`), loaded via its own `<script>` tag, following the exact same pattern already established this session for `round-metrics.js`, `coaching-rules.js`, `valorant-vocabulary.js`, and `gamesense-maps.js` — the app already has a proven, working convention for this, use it rather than inventing a new module pattern. This alone should meaningfully reduce `app.js`'s core size (currently 50,612 lines) without touching anything live.

**Don't attempt a broader `app.js` module-split tonight.** The Theme Builder extraction is safe because the feature is provably dormant; splitting active, load-bearing code (insight generation, profile persistence, the Henrik pipeline) carries real regression risk and deserves its own careful, tested pass — not something to rush through as part of a cleanup sweep. Flag it as a future phase, referencing `notes/structure.md`'s existing recommendation, rather than attempting it now.
